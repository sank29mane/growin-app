## 1. System Classification

**System Type:** Autonomous Agent / In-Memory Simulation-in-the-Loop Backtesting Engine

**Description:**
An in-memory simulation engine integrated into the Growin App algorithmic trading backend. It runs pre-flight trade backtesting and evaluates capital scaling policies (the "risk swarm gate") before submitting orders to the broker. The system uses recent historical ticks and order book depth to simulate the execution of proposed trades. Its primary objective is to prevent catastrophic losses in highly volatile LSE Leveraged ETF markets (e.g., 3LSE, 3SQQ) by dynamically adjusting or blocking orders when the market regime is classified as high-risk by the upstream GMM classifier. Good performance is characterized by an end-to-end execution latency under 50ms, high fidelity in simulated slippage compared to actual execution, and zero safety gate bypasses.

**Critical Failure Modes:**
1. Pre-flight simulation latency exceeds 50ms, causing execution delays that lead to stale orders and bad fills.
2. Fill model accuracy degrades, leading to optimistic simulation of fills (ignoring actual spread and order-book depth of thin leveraged ETFs) and resulting in real-world trading losses.
3. Swarm Gate fails to execute risk scaling policies (e.g., allows 100% allocation during extreme tail-risk regimes due to missing or delayed regime data).
4. Thread-safety/concurrency issues lead to state contamination or race conditions when multiple agent routines query the simulator simultaneously.

### What Domain Experts Evaluate Against

- **Execution Latency:** Good: <50ms end-to-end simulation + gate latency. / Bad: >50ms, causing execution slippage. / Stakes: High. / Source: Execution Desk SLA.
- **Fill Model Accuracy:** Good: Mean Squared Error (MSE) of simulated vs. actual slippage < 0.05% of trade value. / Bad: Optimistic mid-market fills ignoring order-book depth. / Stakes: Critical. / Source: Quantitative Research Desk.
- **Risk Swarm Gate Policy:** Good: Scaling capital allocation down to 0% immediately upon tail-risk regime detection. / Bad: Failing to scale down during vol-spread spikes. / Stakes: Critical. / Source: Capital Risk Committee.

### Known Failure Modes in This Domain

- **Look-Ahead Bias:** Incorporating future information (such as subsequent tick data or future candle high/lows) into the simulation logic, resulting in overly optimistic backtests.
- **Optimistic Slippage:** Simulating full fills at mid-market prices when executing large sizes on thin LSE Leveraged ETFs, neglecting the spread cost and size-dependent market impact.
- **Adapter Hot-Swap Overhead:** Failing to model the latency/cost of switching adapters or executing rapid position reversals, leading to high transaction fee drag.

### Regulatory / Compliance Context

- **MiFID II Compliance:** The simulator and gate serve as the mandatory pre-trade risk controls (kill-switches, price collars, and size limits) required for algorithmic trading systems.
- **Wash Trading / Spoofing Prevention:** Pre-trade checks must ensure the system does not place self-matching orders or engage in patterns that might be flagged as market abuse.

## 2. Framework Decision

**Selected Framework:** Custom event-driven simulator built on NumPy and Pandas

**Version:** NumPy >= 1.24, Pandas >= 2.0

**Rationale:**
Standard Python backtesting frameworks (such as Backtrader or Zipline) introduce excessive object-oriented wrappers, making pre-flight executions too slow (>500ms) for real-time order path gating. A custom implementation using raw NumPy arrays and vectorized Pandas operations runs directly in the application's process memory space with sub-50ms latency (typically 5-10ms). It permits zero-copy array operations and clean thread-safe integration directly into the Python async backend without GIL conflicts.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| `Backtrader` | Performance is too slow for real-time gating; heavy wrapper structures introduce substantial serialization latency. |
| `Zipline-reloaded` | Complex dependency tree and rigid project architecture; difficult to integrate as an inline thread-safe utility. |
| `vectorbt PRO` | Commercial licensing constraints and optimized for batch vector analyses rather than low-latency sequential pre-flight gating. |

**Vendor Lock-In Accepted:** No

### Common Pitfalls
1. **GIL Block on Pandas GroupBy:** Large Pandas operations can block the Python runtime. All high-frequency slicing and calculations are compiled down to raw NumPy.
2. **Off-by-One Lookahead:** Slicing arrays using index values that include the currently forming tick. The index boundaries are strictly enforced to represent only past data.
3. **Memory Leaks:** Storing raw pandas dataframes within the engine class. Data is extracted into primitive float64 NumPy arrays to allow clean GC.

## 4. Implementation Guidance

**Model Configuration:**
- Simulator execution runs purely local on M4 Pro CPU cores (high single-thread performance).
- The risk scaling gate uses regime classifications input by the upstream GMM classifier (Phase 50).

**Core Pattern:**
- Sequential event replay using sliding tick history buffers. The simulator queries a pre-loaded memory view of the last 10,000 tick updates.

**Tool Use:**
- Historical data features and tick profiles are retrieved from DuckDB.
- Custom execution reports are stored locally in SQLite for offline validation.

**State Management:**
- Stateless execution pattern. The simulator takes the current portfolio state and market context, performs a read-only projection, and discards simulator state.

**Context Window Strategy:**
- The engine maintains a circular buffer of the most recent 10,000 observations in RAM to prevent memory fragmentation and keep lookup latency consistent.

### Async-First Design

The simulation engine executes its heavy CPU-bound loops in a thread pool using the async event loop's `run_in_executor` method. This prevents execution path calculations from blocking other asynchronous network requests or WebSockets feeds.

### Prompt Engineering Discipline

Not applicable. The Simulation-in-the-Loop engine is a deterministic numeric validator and does not use Large Language Model prompt interfaces.

### Context Window Management

The size of the sliding historical tick array is locked at 1,000 ticks per pre-flight run to ensure predictable memory boundaries and constant-time slicing.

### Cost and Latency Budget

- Cost: $0 (Local execution on M4 Pro CPU).
- Latency Budget: <20ms for the fill simulation, <5ms for the risk swarm gate checks, leaving a healthy buffer under the 50ms absolute SLA.

## 7. Production Monitoring

**Tracing Tool:** Local SQLite database for query telemetry and custom structured log output.

**Key Metrics to Track:**
1. `simulation_latency_ms` (milliseconds spent simulating fills).
2. `slippage_error_bps` (basis point difference between simulated and actual execution price).
3. `gate_blocks_count` (frequency of Swarm Gate trade scaling/blocking).
4. `active_regime_distribution` (frequency of GMM cluster classifications).

**Alert Thresholds:**
- Average pre-flight latency > 30ms over 5 consecutive cycles.
- Slippage discrepancy > 10 basis points on any trade over 10,000 shares.
- Swarm Gate failure to scale down size when regime input is flagged high-risk.

**Smart Sampling Strategy:**
Save the full historical tick sliding buffer, predicted portfolio states, and execution inputs for any trade where:
- Actual execution price deviates from simulated fill price by > 5 basis points.
- The Swarm Gate reduces order size by more than 50%.
