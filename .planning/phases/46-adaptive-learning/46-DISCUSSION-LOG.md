## 1. Assumptions & Research Resolutions

### Fine-Tuning Engine
*   **Assumption:** Standardize local model fine-tuning on native Apple Silicon `mlx-lm.lora` via Metal GPU acceleration, using QLoRA 4-bit quantized models to train within the strict 60% memory limit (28GB threshold on M4 Pro).
*   **Research Resolution:** Validated. Unsloth/CUDA-bound pipelines would require CPU-only virtualization on macOS, causing unacceptable training slowdowns. QLoRA 4-bit via native MLX is confirmed as optimal.
*   **Confidence:** High (95%+)

### Decoupled Control Loop (Fast-Loop vs. Slow-Loop)
*   **Assumption:** Bypassing autoregressive text generation in the trading execution hot-path (Fast-Loop) by using single-forward-pass logit extraction on a small local model (e.g., LFM 2.5B, Granite 2B) to determine trading recommendations under 20ms. The slow-loop will manage planning (LM Studio) and daily adapter training.
*   **Research Resolution:** Validated. Autoregressive token generation (10ms-20ms per token, 200ms-400ms per block) violates the 100ms trading latency budget. Logit extraction in a single forward pass executes in <5ms on Metal.
*   **Confidence:** High (95%+)

### DuckDB Alpha Feature Pipeline
*   **Assumption:** Training datasets (`train.jsonl` and `valid.jsonl`) will be generated by querying historical market data from DuckDB in `backend/data/analytics.duckdb` via vectorized aggregations.
*   **Research Resolution:** Validated. Leverages existing DuckDB schemas in `backend/analytics_db.py`.
*   **Confidence:** Likely (85%+)

### Dynamic LoRA Adapter Switching
*   **Assumption:** The `MLXInferenceEngine` will handle adapter switching by dynamically loading the specified `adapter_path` using `mlx_lm.load` depending on the active market regime.
*   **Research Resolution:** Updated. Standard `mlx_lm.load()` repeatedly for different adapters causes a 0.8s to 1.5s reload latency and a 2x RAM spike (up to 10GB). However, we can patch this in-memory by loading target adapter weights using `mx.load()` and applying them using `model.update(tree_unflatten(list(weights.items())))`, followed by `mx.eval(model.parameters())`. This drops switching latency to 10-50ms and avoids base model RAM spikes.
*   **Confidence:** High (95%+)

### Local Memory Constraints (LM Studio vs. MLX)
*   **Assumption:** Concurrently running LM Studio models and native MLX models must stay within a 60% system memory limit (~28GB threshold) to prevent macOS swap files from degrading GPU performance.
*   **Research Resolution:** Validated. Swapping to SSD triggers extreme latency and must be avoided by memory throttling.
*   **Confidence:** Likely (90%+)

### Apple Neural Engine (ANE) for NeuralJMCE
*   **Assumption:** Custom mathematical layers (such as Cholesky decomposition or Fourier transforms) in NeuralJMCE could be accelerated by ANE when compiled to CoreML.
*   **Research Resolution:** Corrected. The ANE does *not* support Cholesky or Fourier transform (FFT) layers. CoreML compilation would partition the model and fall back to CPU (Accelerate) or GPU (Metal/MPS) with significant MLCustomLayer context-switching overhead. The model must be split: standard neural feature extraction runs on the ANE via CoreML, while mathematical transforms execute directly on CPU (Accelerate) or GPU (MPS/Metal).
*   **Confidence:** High (98%+)

## 2. Agreed Implementation Decisions

1.  **D-16:** Standardize on native macOS MLX fine-tuning (`mlx-lm.lora`), bypassing CUDA-bound Unsloth.
2.  **D-17:** Implement in-memory LoRA weight hot-swapping in `mlx_engine.py` using `model.update(tree_unflatten(list(weights.items())))` and `mx.eval(model.parameters())`.
3.  **D-18:** Partition NeuralJMCE: execute feature extraction on ANE (via CoreML) and mathematical transformations (Cholesky/FFT) on CPU (Accelerate) or GPU (Metal/MPS).
4.  **D-19:** Enforce the 60% system memory limit (~28GB VRAM/RAM limit on M4 Pro) across LM Studio and MLX runtime environments.
